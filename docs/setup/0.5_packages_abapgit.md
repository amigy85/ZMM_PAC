`FOLDER_LOGIC=PREFIX`).

## Estrutura a reproduzir (folder logic PREFIX)

| Package | Pasta | Descrição (CTEXT exacta) | Super-package |
|---|---|---|---|
| `ZMM_PAC` | `/src/` | `Plano Anual de Compras - raiz` | — (topo) |

> Descrições sem acentos de propósito (como nos metafiles). O primeiro pull
> sobrepõe o CTEXT a partir do Git, logo não há diff fantasma.

## Passo 1 — Ordem de transporte

Em SE09/SE10, criar (ou identificar) uma ordem de transporte **Workbench** no DEV
para os 4 packages e, depois, os objectos. Guardar o nº → registar no `proposal.md`.

## Passo 2 — Criar o package raiz `ZMM_PAC` (SE21 ou SE80)

- Package: `ZMM_PAC`
- Short text: `Plano Anual de Compras - raiz`
- Software Component: `HOME`
- Application Component: `MM-PUR` (ou o que a equipa usar)
- Transport Layer: a camada **transportável** padrão do DEV (confirmar com a Basis;
  **não** `$TMP`/local)
- Gravar e atribuir à ordem do Passo 1.

## Passo 3 — Criar os 3 sub-packages

Para `ZMM_PAC_DATA`, `ZMM_PAC_CORE`, `ZMM_PAC_UI`, igual ao Passo 2, mas:
- Short text conforme a tabela.
- **Super Package = `ZMM_PAC`** (cria a hierarquia que o PREFIX espera).
- Mesma Software Component `HOME`, mesma ordem de transporte.

> O nome tem de ser exactamente `ZMM_PAC_DATA/_CORE/_UI`. Com PREFIX, o abapGit
> deriva a pasta retirando o prefixo do super-package. Nome trocado → erro
> "Unexpected package naming".

## Passo 4 — Pré-requisitos do abapGit online no CBD

- Certificado do `github.com` carregado em **STRUST** (SSL client Standard) e ICM
  com SSL activo.
- Se o repositório GitHub for **privado**: ter **utilizador + PAT de leitura** do
  GitHub para introduzir na definição do repositório no abapGit.
- Se **público**: SAP lê sem credenciais (mas o código fica exposto — desaconselhado
  para código interno).

## Passo 5 — Ligar o repositório (abapGit → + New Online)

- URL: `https://github.com/amigy85/ZMM_PAC.git`
- Branch: `change/add-pac-catalog-upload`
- Package: `ZMM_PAC`
- **Folder Logic: PREFIX**
- Credenciais do GitHub se privado.

## Passo 6 — Pull e verificação

- Fazer o **pull**. Nesta fase `/src/` só tem os `package.devc.xml`, logo o pull
  apenas confirma/alinha os 4 packages — serve de teste à ligação e à folder logic.
- Verificar: **sem diffs fantasma**; os 4 packages com a hierarquia correcta.

## Passo 7 — Registar

Registar o nº da ordem de transporte no `proposal.md` (secção "Ordem de transporte")
e marcar a 0.5 no `tasks.md`.

## Erros comuns (CLAUDE.md §6)

- "Package has a sub-package with the same name" → hierarquia mal montada (Passo 3).
- "Unexpected package naming" → nome fora da convenção PREFIX.
- Ficheiros sempre "modificados" após cada pull → LF/BOM (prevenido pelo
  `.gitattributes`).
